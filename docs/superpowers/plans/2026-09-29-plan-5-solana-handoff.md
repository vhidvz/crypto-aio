## 2. Rulings F5-R1–F5-R24

Each entry gives the decision, then why. **Fund-critical** marks a ruling without which a transfer could pay twice, a deposit could be dropped, or an Operation could burn fees without a bound. F-R1 (the user's) is in §4.

- **F5-R1 (lesson 19).** Hand-encoded integers are range-checked with fixed-text errors, never wrapped. Why: 2^64 + 5 lamports encoded silently as 5.
- **F5-R2 (A28).** The `public` preset sets `{ rps: 4 }` from Solana's published per-IP limits; lesson 19 boundaries are tested (u64 amounts `INVALID_AMOUNT`, u8/u32 fields `INVALID_INTENT`); presets are deep-frozen; base58 input is capped at 44 or 88 characters before decoding (lesson 20).
- **F5-R3.** A recent price above 2^64 − 1 − 999 is malformed (retryable), which leaves room for the D10 variant; Task 7's broadcaster passes the node's `rpcData` to the classifier, which can only make `rejected` rarer.
- **F5-R4.** The native `Connection`'s `close()` clears rpc-websockets' armed reconnect timer, and `requestAirdrop` carries broadcast tags. The jayson → ws unmet-peer warning at install is harmless (recorded here, as ruled).
- **F5-R5.** The scripted node snapshots state per block; agave facts are confirmed from v4.3.0 source or left and noted; the harness keeps a fixed id and `random`.
- **F5-R6 (lenient readers).** Outer instructions keep the 1,232-byte cap, but an inner (CPI) memo is never refused: above 10,240 characters it attaches no memo and marks the transaction `partial`. Why: one CPI-memo transaction could stall every deposit scan, since a block parse is all-or-nothing.
- **F5-R7.** `observe` may run the landing guard on a `confirmed` monitor read, as observed evidence only; the verdict rules bind `includedFinal`. A mint every quorum endpoint calls absent stays cached as `ASSET_RESOLUTION` (a core rule, §5).
- **F5-R8 (lesson 20).** Account data is checked by a linear base64 round trip, and the first-available clamp runs only on a real RPC code. Why: the repeated-group regex threw V8's `RangeError` above about 3.2 MiB, on valid 10 MiB accounts.
- **F5-R9 (fund-critical: a node's height is a claim).** Build records the blockhash's context slot, and the expiry proof attests under the proof quorum that the finalized block at that slot carries the message's blockhash and sits 150 blocks below `lastValidHeight`, or decides nothing. Why: one build-time endpoint reporting a lower height made the monitor prove "expired, absent" while the transaction could still land, and `rebuild` paid twice. Its (b), the price ceiling, and (c), the Task 7 minors, went to the final wave.
- **F5-R10 (fund-critical: the attested anchor).** When the quorum attests that the block at the saved slot carries our blockhash, its height + 150 is `L`; a recorded height that disagrees is a logged build-time lie, and anything else decides nothing.
- **F5-R11 (fund-critical).** F5-R10 holds under four pinned conditions: the anchor's quorum key is `{height, matches}`; "finalized past L" is re-run at the attested `L` in both `expired` and `includedFinal`; the attested `L` feeds the window, the memo and the scan; only a hash match adopts a height. A slot-free fallback attests the block at `L − 150`.
- **F5-R12.** `exports` and `typesVersions` keys stay alphabetical (the board's merge convention), and the rule moved to `test/architecture/packaging.test.ts`; the guides state Node ≥ 22.12, and a pack-install-load smoke test runs at merge.
- **F5-R13.** A build-time lie in both the slot and the height leaves the Operation stuck, never paid twice: an accepted liveness residual. The re-review found that the stored blockhash matching the message is a safety precondition, not liveness (F5-R14).
- **F5-R14 (fund-critical: the raised-height slot path; `SolanaExpiryOrdering` is a store safety precondition).** On the not-yet branch of both `includedFinal` and `expired`, a raised recorded height is checked through the recorded slot alone (no fallback; any failure is "not yet"), and only a hash match adopts the attested height, after which the predicate runs again (final-wave B2). A store keeps `attempt.ordering` whole and unmodified, because a changed `blockhash` misplaces the window and can pay twice; the guides say so, and the store-contract pin is Plan 7's.
- **F5-R15 (fund-critical; lesson 21).** Solana's only `rejected` is a signature failure, and it stands only when our sent bytes carry a signature that fails the core's own ed25519 verifier (`zip215: false`); otherwise the result is `refused`. Task 10b landed it before the final wave. Why: a lone endpoint claiming a bad signature, then relaying, ended the Operation, and a caller's retry paid twice.
- **F5-R16.** Task 10's test minors landed with 10b (signing counts after finality, the winning Attempt, the stored message is the signed one, step budgets below Jest's timeout); the wall-clock store and the `randomBytes` seeds joined the Plan 7 determinism item.
- **F5-R17.** Task 10b accepted: a liar that keeps, relays or never relays our bytes ends paid once, and a stalled Operation reaches `expired` through the background monitor alone.
- **F5-R18.** The monitor never resends a stalled transfer (core policy); the guides say to retry only with `rebroadcast` or the same idempotency key, never a new key.
- **F5-R19.** Task 11 accepted. The preset keeps its published rate (A28) and the guides document the observed `getBlock` limit; Node 22.0–22.11 get Node's raw `ERR_REQUIRE_ESM` (documented; a guided error is Plan 7's); `.env.example` gained the Solana variables.
- **F5-R20 (fund-critical: C1, the resumable window proof).** The 151-block "not included" proof never completed on a rate-limited provider, so it resumes across passes: a frame per window and a cursor per signature (at most 1,024 each), every read under the proof quorum, nothing memoized before the window is final, every resumed step re-chained from the attested blockhash to the attested top, and a broken chain dropping both, so no memo can give a false "not included". It completes in 27 passes under 6 `getBlock` per 10 s. Also: the window test has its own flag (I1), `RETRY_MS` is 11 s, the test reads 100 blocks deep, and the preset comment is corrected.
- **F5-R21.** A `## Solana safeguards` section in `security.md`, plus a checklist line (the Plan 3 convention).

- **F5-R22 A1 (fund-critical: `maxComputeUnitPrice`, the fee ceiling).** A per-handle bound (bigint µ-lamports per CU, 999 to 2^64 − 1, default 10,000,000; options › `network.params` › default; unknown keys `CONFIG_INVALID`, listing the accepted name, never echoing the key) clamps speeds to min(percentile, cap − 999) + variant, refuses an override above it with `INVALID_INTENT` before any request, and is re-checked in `build` (`signedFee`). Why: one READ endpoint could make a transfer spend the wallet's whole SOL balance in priority fees and still end `final`; the worst is now 5,000 lamports plus 0.014 SOL per transfer.
- **F5-R22 A2 (fund-critical: watched token accounts in scans).** A filtered scan matches a watched token account as the source or destination of a successful classic transfer, and an SPL `transfer.to` names the owner wallet. Why: SPL deposits into a watched ATA were dropped silently.
- **F5-R22 A3 (fund-critical: assemble binds the ordering; decimals under the proof quorum).** `assemble` refuses with `SIGNING_FAILED` unless the ordering is `expiry`, its blockhash is the message's recentBlockhash, and its height and slot are bigints; mint decimals are read under the proof quorum in the estimate and the build, so a lagging endpoint decides nothing.

**Lessons and notes (binding where TON has the analogue):**

- **A node's build-time answer is a claim (F5-R9–R11, F5-R14).** Store the signed fact in the ordering, bind it in `assemble` (F5-R22 A3), attest it under the proof quorum at its own height, adopt a node's number only on a hash match, and re-run the predicate at the attested value. A raised claim must reach the attested path, not stall.
- **A proof that walks many blocks must survive rate limits (F5-R20).** Proof-quorum reads fail at once while a `Retry-After` is pending, so a proof that needs more reads than one pass allows never completes. TON's authenticated walk (F6-R21, F6-R29), which F6-R34's replay guard reruns before every send, should be measured against toncenter's keyless 1 rps. If it is exposed, copy the frame-plus-cursor memo: memoize only quorum-attested final data, key it by every fact the proof depends on, re-verify each resumed step from the attested start, and bound it.
- **An operator fee bound no endpoint can raise (F5-R22 A1, F4-R28).** Clamp node-suggested prices to it, refuse an explicit fee above it before any request, and re-check it in `build` whatever produced the fee object. TON confirms its gas and forward-fee bounds (board).
- **Deposits into derived accounts (F5-R22 A2).** Where tokens arrive in an account the wallet owns (Solana ATAs, TON jetton wallets), a filter or history that watches either address must return the deposit, and `transfer.to` names the owner.
- **Decimals under the proof quorum on every signing path (F5-R22 A3)**, not only in `getTokenMetadata`.
- **Handle options.** Unknown keys are `CONFIG_INVALID`, list the accepted names and never echo the key (TON's F6-R25 pattern, which Solana copied).
- **Readers.** A cap derived from what we send never refuses chain-valid data a scan reads (F5-R6); large payloads get linear checks, never a repeated-group regex (F5-R8).
- **Opt-in tests.** A live test that needs a keyed or self-hosted endpoint is gated on its own flag and its URL (N1). Give CPU-bound tests an explicit timeout (N2).
- **`engines` stays `>=22`.** Solana is an optional peer, and the guides state Node ≥ 22.12 for it; raising `engines` would bar every other family's users on 22.0–22.11.
