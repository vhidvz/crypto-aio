## 2. Rulings F6-R1–F6-R37

Each entry gives the decision, then why. **Fund-critical** marks a ruling without which a transfer could pay twice or be mis-scaled, a deposit could be dropped or credited twice, or an Operation could burn fees without a bound. F-R1 (the user's) is in §4.

- **F6-R1 (A28).** The keyless presets take `{ rps: 0.5 }` and the keyed `{ rps: 5 }` per API. Why: toncenter's published limit (1 rps keyless, 10 with a free key) is per network across v2 and v3, and A28 splits one published limit between the presets that share it.
- **F6-R2.** Own-key preset lookups (`Object.hasOwn`), native metadata read from `TON_CHAINS`, the USDT name's source, and an accurate rate-limit note. A shared `deepFreeze` and one bucket per host across transports go to Plan 7.
- **F6-R3.** The keyed presets set `burst: 1`. Why: with the default burst, v2 and v3 together sent about 18 requests in the first second after idle, against a limit of 10.
- **F6-R4 (lesson 20).** Comments are read iteratively (at most 256 cells), a BOC's header cell count (at most 2^13 for bodies) is checked before `Cell.fromBoc`, `toRaw` returns null for a foreign workchain, and an echoed key name is capped. Why: `@ton/core`'s recursive snake reader is quadratic, 3.6 s for one 1 MB comment.
- **F6-R5.** The scripted node is never more lenient than the chain: a dust bounce is `nofunds`, an unpayable message without +2 rolls the seqno back, a frozen wallet is not revived by its `StateInit`, and a jetton wallet checks the TEP-74 sender (707). Why: later verdicts depend on each of these paths.
- **F6-R6 (fund-critical; lesson 6 sharpened).** A missing or ill-typed verdict field is malformed and retryable, never `false` or 0; a lookup by message hash keeps only answers about the hash asked; amounts and counts are range-checked. Why: a truncated indexer answer, which every endpoint on the same indexer agrees on, became a terminal `failed`, and a caller's new-key retry pays twice.
- **F6-R7.** Node fidelity, round 2: no bounce on an action failure without +16, the chain's own refusal texts, and `estimateFee` on an undeployed wallet as the liteserver answers it.
- **F6-R8.** An over-long or ill-typed jetton name or URI is absent; only symbol and decimals are refused. Why: author-set text that every endpoint agrees on would retry forever.
- **F6-R9 (fund-critical; lesson 21).** TON never returns `rejected` from node text: only our own parse of bytes that do not decode is `rejected`, and every refusal waits for the proven expiry (about 60 s). Why: toncenter's refusals are unstructured text on HTTP 500.
- **F6-R10.** The classifier's 1,024-character cut never makes a success; network params and capabilities are strict allowlists; "not now" answers (`LITE_SERVER_NOTREADY` and three pool texts) are retryable and ambiguous.
- **F6-R11 (fund-critical: the seqno-replay fix).** A failed wallet run is `pending`, not `failed`, unless it consumed its seqno (`consumesSeqno`: the action phase succeeded, or compute failed with 137 after commit). Why: the brief's `failed` for an action failure left the seqno replayable, and the node test moved 1 GRAM after the verdict.
- **F6-R12 (fund-critical: the bounce-flag rules).** The verdict follows the signed bounce flag: a bounce phase on a non-bounceable delivery, or a failed bounceable delivery without one, is `PROVIDER_INCONSISTENT`, never `failed` (a re-send pays twice) or success (a phantom); the chain's counters are cross-checked; pagers page on the raw page, never on a filtered length. A failed batch must never be re-sent whole (F6-R15).
- **F6-R13 (fund-critical: decimals).** Decimals are never defaulted for linked jetton content (TEP-64's 9 applies only to fully on-chain content), so a token whose metadata omits them stays unresolved. The metadata read is pinned under the proof quorum, chunked content is read, an ill-typed field is the token's own `ASSET_RESOLUTION` only when every endpoint agrees, and `ext.ton.jettonWallet` reads under PROOF. Why: the brief's default of 9 would have cached a 1,000× mis-scale for the container's life.
- **F6-R14.** Two Task 7 minors went to the final wave: a bounce message whose `bounced` flag is missing is no contradiction, and a comment on the chain's global version 8.
- **F6-R15 (fund-critical: single-output transfers).** One output per transfer: `batch-transfer` is off, and more than one output is `UNSUPPORTED_CAPABILITY` before any I/O. Why: each TON message lands in its own transaction, so a batch can be partly delivered, and the core has no per-leg outcome: `failed` invites a whole re-send that pays the landed legs twice, and `confirmed` hides a bounced leg. TON batch payouts (spec §15) are deferred past 0.1.0, recorded as a deviation in the CHANGELOG and the guides.
- **F6-R16.** The config forward fee (param 25, or 24 with the masterchain) is a floor under the estimate, and the network charge has a ceiling (1 GRAM basechain, 100 masterchain).
- **F6-R17 (fund-critical: the funds path and the fee ceiling).** An empty emulation (tonlib sizes gas by the balance, so an unfunded wallet reports 0) is `INSUFFICIENT_FUNDS` only below the transfer's known minimum; the rebuilt request binds send mode 3 exactly, no custom payload and no extra currencies; the ceiling becomes a validated per-chain setting. Why: an unbound mode 128 would sign away the balance, and a fresh wallet retried forever.
- **F6-R18.** Superseded by F6-R21: an indexer-based fix for a deleted seqno-0 wallet. Its guide rule stays: never share a wallet key.
- **F6-R19.** A gas floor joins the funds minimum (its formula corrected by F6-R20); `estimateFee` may throw `INSUFFICIENT_FUNDS` with `required` a lower bound before gas, as EVM does.
- **F6-R20 (fund-critical: the fee ceiling).** A config forward fee above `maxNetworkFee` is a retryable `PROVIDER_INCONSISTENT`, checked before the balance; the gas floor is `flat_gas_price` alone (param 21 basechain, 20 masterchain). Why: one endpoint inflating param 25 failed a funded wallet's Operation definitively, and `flat_gas_limit × flat_gas_price` overstated the floor about 100×.

Now the only `included: false` rests on the wallet's own raw liteserver transactions, each hashed locally and hash-linked back from an account state bound to the attested block; a consumer is decoded from its signed header; a deletion, activation or chain start in the window decides nothing unless the chain shows ours; the indexer is a positive hint only; the node models deletion and re-deploy.

**What core changes must keep for TON:**

- **Orderings stay whole.** A TON Attempt's ordering is a `TonSeqnoOrdering`: `kind: 'seqno'`, a bigint `seqno`, and the numbers `validUntil` and `validFrom`. A store that drops `validFrom` costs liveness (the proof and the guard fall back to a one-day window); one that moves it later can hide a reset, prove "not included" falsely, and `rebuild` pays twice. `assemble` binds it to the signed bytes, as Tron and Solana do.
- **The replay guard's facts.** The guard lives in the TON broadcaster because the port carries no ordering: `assemble` records `validFrom` and `assembledAt` per TEP-467 hash (4,096 entries). A core resend hook must keep "undecided → not sent, retryable, recorded ambiguous", never `refused`, because a non-retryable `TX_REFUSED` invites a caller's new-key retry. Keep the first-send exemption bounded in time.
- **The cache rule junk jettons rely on.** Missing, unindexed or decimals-less metadata is a non-retryable `PROVIDER_UNAVAILABLE`, so R35 reports the transfer raw and unresolved, and N6 caches nothing (it caches only `ASSET_RESOLUTION`). A change to R35 or N6 must keep the junk-jetton e2e tests (P2, P3) green and never cache a "not yet". Decimals are never defaulted (F6-R13).
- **Rate limits.** Measure any transport change (per-method limits, probe backoff, a token wait for trials) against TON's walk: the proof's `includedFinal` and every guarded resend read it under the proof quorum.
- **Deposits.** TON history is one indexer's `observed` read. Jetton deposits are credited only from the arrival in the owner's jetton wallet (`msg:in:jetton` in the history of `bc.ext.ton.jettonWallet(owner, master)`); the TON guide and checklist state TON's exception to the general "credit only on `proven`" line.

**Lessons (binding where a family has the analogue):**

- **Resending the same signed bytes is not idempotent where replay protection can go back** (F6-R34). A TON seqno returns after a delete and a re-deploy from the public `StateInit`. Guard every resend path (a same-key retry, the `dropped` rebroadcast, `recover()`, `rebroadcast`, a bare broadcast), and bound any exemption in time (F6-R37 N1).
- **"Not included" from self-authenticating chain data** (F6-R21, F6-R29).
