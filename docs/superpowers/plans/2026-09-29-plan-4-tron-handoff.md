## 2. Rulings F4-R1–F4-R29

Each entry gives the decision, then why. **Fund-critical** marks a ruling without which a transfer could pay twice, a deposit could be dropped, or an Operation could burn fees without a bound. F-R1 (the user's) is in §4.

- **F4-R1 (A28).** No Tron preset sets `rateLimit`: TronGrid publishes no keyless rate ("do not hard-code fixed limits"), and the guide tells production users to set one or use a key. The board's A28 was corrected to say so.
- **F4-R2.** Network options are a strict allowlist; an unknown key is `CONFIG_INVALID` that lists the accepted names and never echoes the key. The capability-override guard went to Task 9 (F4-R16); one shared `deepFreeze` goes to Plan 7.
- **F4-R3 (lenient readers).** `readRaw` (history and scans) keeps client-set fields java-tron leaves unbounded, such as a .NET-ticks timestamp above 2^53 (a real vector from block 86,615,431); `decodeRaw` of our own bytes stays strict; base58check never runs on more than 34 characters (lesson 20). Why: refusing real chain data stalls history.
- **F4-R4.** The scripted node follows java-tron v4.8.2.2 source, fetched read-only and cited in comments (admission order, texts, actuators); where the source settles nothing, the brief's behaviour stays and says so.
- **F4-R5.** `triggerconstantcontract` gets a verdict-only quorum key (honest nodes never agree on its whole answer); token metadata is read under `quorum: 'proof'`, balances plainly; history sends `search_internal=false`; a 401/403 on a proof read stays retryable (TronGrid documents 429 or 403 for rate limits); `{}` keys as absent; heights, cursors and messages are capped.
- **F4-R6.** The node serves genesis as java-tron does (no number, timestamp, version or witness signature), hashes the re-serialized raw, and `place()` applies the key-independent checks at mining.
- **F4-R7 (fund-critical: history never drops an entry with an id).** An entry is skipped only when it has no id of its own and carries TronGrid's documented internal shape (64-hex `internal_tx_id` and `tx_id`); anything else is malformed and retried (final-wave A2). Why: the old `internal_tx_id` skip would drop deposits silently after a schema drift. Plan 7: a structured status on `PROVIDER_MISCONFIGURED`, and a `JSON.rawJSON` note for custom transports.
- **F4-R8.** Unknown, empty and `OTHER_ERROR` broadcast codes are possibly sent (retryable, ambiguous); size texts are `rejected` only where consensus agrees. Broadcast fanout's first HTTP 200 answer goes to Plan 7 with EVM's R64.
- **F4-R9.** A missing `energy_used` is malformed, and the fee model refuses energy or bandwidth ≤ 0; `classifyBroadcast` runs inside the broadcaster, never under a quorum.
- **F4-R10.** Impossible answers decide nothing: an included TRX transfer that is not SUCCESS, non-canonical call data, a `getcontract` answer without an address. A live check found `receipt.result` on early TVM receipts (block 3,300,000), so the strict rule stays.
- **F4-R11.** The expiration is anchored at min(head time, local clock), which can only shorten the window; the negative proof reads the signed expiration against attested block times. The pre-sign TRX-to-contract check (final-wave B2) runs only where `getForbidTransferToContract` is 1, and it is 0 on mainnet, Nile and Shasta.
- **F4-R12.** The negative proof's floor is the attested reference block, never a clock-derived `expiration − MAX_EXPIRATION_MS`, which a forward-dated head plus a leading clock could push above the inclusion (a two-fault double pay; the root of F4-R13–R14). The final wave refuses a head ahead of the clock and verifies the signature in `assemble`; the span cap became moot.
- **F4-R13 (fund-critical: the reference hash).** Task 8's design is accepted: the ordering records `lastValidHeight` (the reference height plus 65,536, java-tron's TaPoS window) and the signed `ref_block_hash`, and `assemble` binds both to the signed bytes.
- **F4-R14 (fund-critical: the forged-reference-head double pay).** A build-time endpoint could forge a head whose signed low 16 bits name a block 65,536 lower; the transaction landed below the recorded height, the proof answered "not included", and `rebuild` paid twice. Now the stored height counts only when the attested solidified block there carries the signed hash; otherwise the proof searches every height sharing the signed low 16 bits, from one TaPoS window before the 24 h mark up to the top, and scans each match. A missing or malformed hash decides nothing; a pool-only history entry retries; the head walk is bounded; `blockTimeStamp` joined the receipt key.
- **F4-R15 (fund-critical: `TronExpiryOrdering`).** A typed ordering (`kind: 'expiry'`, `expiresAtMs`, `lastValidHeight`, `refBlockHash`: 16 lower-case hex, the 8 signed bytes) exported from `crypto-aio/tron`, structurally inside the core `expiry` variant, with no core change. A store must keep it whole and exact: a changed hash or height, or a rounded-down `expiresAtMs`, can prove `expired` while a block holds the transaction. Its typed core home goes to Plan 7.
- **F4-R16.** The capability guard runs at driver creation and is stricter than EVM's on `remove`. Why: removing `expiry` would disable the negative proof.
- **F4-R17 (the SDK boundary).** Each family's lazy test lists only its own SDK, so a Tron module importing ethers would pass: a cross-family architecture test goes to Plan 7. The overclaiming plugin-test title was renamed (B4).
- **F4-R18 (fund-critical: the reference-hash proof).** The Task 8 fix is accepted with liveness-only concerns: no "not included" rests on an unverified height, though a lying head can still force retries or a long scan.
- **F4-R19 (fund-critical: the search's bound).** The fast path also stops at the first block at or past `expiration − 24 h`, as the search does (A3), so a lying build head naming a real day-old block costs at most a day of blocks, never 65,536. Why: request amplification, never a wrong answer.
- **F4-R20 (fund-critical; lesson 21).** Task 10 reproduced a double pay end to end: a lone endpoint answering "Amount must be greater than 0." for our valid bytes ended the Operation `failed`, and a later relay plus a caller retry paid twice. Task 10b was pulled forward: the broadcaster re-reads the bytes it sent and keeps `rejected` only when the claim holds for them (a signature under 65 bytes, no contract, TRX to its own sender, a non-positive amount, over 512,000 bytes); anything else is a non-terminal `TX_REFUSED`. The monotone highest height and the transport-id option go to Plan 7.
- **F4-R21.** Task 10's review minors are folded into Task 10b as a separate test commit.
- **F4-R22.** Task 10b is accepted; codec and classifier share one SDK-free protobuf reader (B5); the mutation-sweep restore rule went on the board (§6).
- **F4-R23.** Both byte rules need exactly one signature, and the size rule exactly 65 bytes (java-tron reads only the first 65, so a padded copy could land smaller); the persistent-liar test (proven `expired`, one signature) is committed; the guides say a `TX_REFUSED` transfer is repeated only with the same idempotency key.
- **F4-R24.** The opt-in suite keeps two live checks beyond the brief: a strict "not included" proof for a random txID, and the head's age. Keyless mainnet TronGrid answers 429 and the probes then exclude the endpoint; the guide sends mainnet to a key or another provider, and the core fix goes to Plan 7.
- **F4-R25.** Opt-in suite fixes: 120 s and 180 s budgets with a short synthetic expiry; the head age measured the builder's way, with a two-cause error; at most 3 retries, on retryable errors only.
- **F4-R26.** Task 12 is accepted; `.env.example` gains the two integration variables; the owner's `[0.1.0]` CHANGELOG line ("planned") goes to Plan 7.
- **F4-R27.** Docs fixes (C1): use three proof providers (two tolerate an outage, not a liar during one: the core drops a request-dead endpoint from the count after about 45 s, P25-R21); only bandwidth and energy can be 0; `lifecycle.broadcastFanout` ≥ 2; keep the server clock in sync. The guide merge map went to the merge step (§3).
- **F4-R28 (fund-critical: `maxFeeLimit`).** The fee-limit ceiling, energy estimate, energy price and token balance all came from one unchecked READ endpoint, so an `assert`-style failure could burn up to 15,000 TRX, or the whole balance under a forged ceiling. Now a per-handle `maxFeeLimit` (sun as a bigint, 1 to 2^53 − 1, default 100 TRX; options › `network.params` › default) makes the fee limit min(estimate × margin, node ceiling, `maxFeeLimit`). A simulated need above it is a non-retryable `INVALID_INTENT` before signing, naming the option, with `details: { required, maxFeeLimit }`; `build` and `assemble` bound it again. No endpoint can make one Operation burn more than `maxFeeLimit` in energy.
- **F4-R29.** The final-wave re-review approved the merge. N1 (the TRX-to-contract flag is one endpoint's word) and N2 (the scripted node's genesis time) go to Plan 7.

## 5. Plan 7 items raised by Plan 4

- **Lesson 21 beyond Tron.** Tron has it (`c9326d5`, `a2cf389`). EVM still needs it, with the core option that a first-broadcast `rejected` needs a second endpoint. The broadcast fanout takes the first HTTP 200 answer (F4-R8 (3), with EVM's R64).
- **Probe 429s (F4-R24).** Keyless TronGrid mainnet fails live: HTTP 429, then "no healthy endpoint". TronGrid publishes no rate, so the presets set no `rateLimit`, and Plan 2.5's in-bucket probes do not apply. A height-probe 429 clears the height; an identity-probe 429 locks the endpoint out for 15 s. Instead, back off and keep the last good height and identity. Also measure the per-method 429 exposure (F5-R20) for Tron's reference search, which reads up to a day of blocks under the proof quorum; Plan 4 did not.
- **The SDK boundary (F4-R17).** One cross-family architecture test: an adapter under `src/adapters/<family>/` imports only its own peer SDKs, and only from its SDK-boundary module (Tron's `codec.ts`). Watch `require.cache` by resolved path (with F3-R16). Tron's `lazy.test.ts` still lists only tronweb; UTXO's shape reads every peer.
- **The monotone highest height (F4-R20 (2)).** The transport's highest-seen height only rises. One probe that sees a forged far-future head makes every honest view look stale until restart, so nothing in that container confirms (liveness). It needs attestation or decay.
- **Determinism (F4-R20 (3)).** `CryptoAio` cannot inject the transport id or `random`, so Tron's e2e pins `Math.random`, as UTXO's does. One container option covers every family, with the EVM harness, a clock for `MemoryOperationStore`, and seedable build variants (Tron's D5 offsets use `randomBytes`).
- **F4-R29.** N1: read `getForbidTransferToContract` under the proof quorum with a key that projects only it. Today a false 1 refuses a valid transfer before signing, and a false 0 lets the chain refuse it; liveness only. N2: the scripted node serves genesis with timestamp 0 but applies expiry with an internal slot time; make it apply the served time.
- **Orderings in the core (F4-R14 M3, F4-R15).** The store contract suites pin only nonce orderings; add expiry orderings with Tron's `refBlockHash` and Solana's shape. Give the ref hash a typed core home (one rename of `TronExpiryOrdering`). `ProofSource.includedFinal` receives no signed bytes, so proofs read the expiry facts from the stored ordering.
- **Economic ceilings (F4-R28).** Tron's `maxFeeLimit` is a model for the cross-family fee-ceiling policy. EVM has no operator bound: `gasLimit` and `maxFeePerGas` come from the node.
- **Confirmed from earlier lists:** the `HttpTransport` response byte cap (F4-R3); a structured HTTP status on `PROVIDER_MISCONFIGURED` and the `JSON.rawJSON` note (F4-R7); one shared `deepFreeze` (F4-R2); the bounded-name helper, since Tron's `named()` still echoes a capability name of up to 40 characters (F3-R16).
- **Secrets (F3-R20, the release blocker).** Tron adds no fragment surface, because the key is the whole `TRON-PRO-API-KEY` header value; include it in the fragment tests anyway.
- **Scanner trust (final review, declined).** Tron's scanner, like EVM's, reads blocks and the finalized tip under MONITOR, with no binding of the transaction list to the header hash. Old mainnet blocks where `gettransactioninfobyblocknum` lists fewer infos than transactions are unverified; they would stall a backfill (retryable), never answer wrongly.
