## Review Focus

These five inputs are the most likely to bite a real user after this plan, and no spec example exercises them. Each has a pinned test in the task named.

1. **An exchange-sized balance above 2^53 − 1 base units**, read by a driver that sets `exactIntegers`, must come back as the exact `bigint`, and a proof quorum must tell apart two answers that `JSON.parse` would round to the same number. Pinned in Task 1 ("lets quorum keys see the revived values" and "tells apart answers that round to the same number").
2. **A keyless 1 request/second endpoint** (toncenter, TronGrid, public Solana): `refreshHealth()` followed by a monitor read must not provoke HTTP 429 from its own probes, and the endpoint must end `healthy`, never excluded for an unknown height. Pinned in Task 2 ("keeps a 1 request/second endpoint healthy through probes and reads").
3. **One endpoint that over-reports its head** must never become the only endpoint of a `quorum: 'proof'` read; with two endpoints both are asked, and when the honest set is too small the read decides nothing (retryable). Pinned in Task 3 ("never lets one over-reporting endpoint become the sole proof endpoint").
4. **Registering the built-in EVM plugin again** (`new CryptoAio({ plugins: [evmPlugin()] })`, `aio.use(evmPlugin())`) must stay a no-op, while a different plugin reusing a registered name must fail with `CONFIG_INVALID`. Pinned in Task 8 ("keeps use() idempotent for the same plugin, built-ins included").
5. **An `xpub` on an EVM or fake testnet** (EVM wallets export `xpub` on every network) must keep deriving deposit addresses, while a Bitcoin mainnet `xpub`/`zpub` on a UTXO test network (or `tpub`/`vpub` on mainnet) must be refused with `CONFIG_INVALID`. Pinned in Task 9 ("checks the extended key network class on UTXO chains only (A20)" and "refuses an extended key of the other network class").

## Decisions recorded by the plan author

Rulings A5–A22, lessons 1–18 and the Plan 2.5 brief bind this plan. Where they and the spec were silent, these decisions were made; each names what it costs if wrong.

- **D1. One `exactIntegers` implementation (A12, amended).** Plan 4's and Plan 5's Task 0 are merged: one `parseJson(text, exactIntegers)` helper in `src/core/util/json.ts`, one `CallOptions.exactIntegers` field, threaded through `rpc`, `rpcRaw` and `http` to `#exchange`, and one test file with both plans' assertions. Health probes (`#direct`) keep plain parsing: they read ids and heights, which are safe integers. Cost: none beyond the field.
- **D2. Probes take tokens (A17).** Every probe request (`EndpointCall.rpc`/`http`, i.e. `#direct`) first takes a token from the endpoint's own bucket, bounded by the probe's own deadline, exactly as a request does in `#attempt`. A probe that cannot get a token in time fails like any other probe failure. Probes do not also wait for a `Retry-After` window (`notBefore`): a server that still answers 429 to a probe inside the configured rate is misconfigured (its `rateLimit` is too high). Cost: `ready()` on a 1 request/second endpoint takes about 2 s (identity, then height) instead of failing.
- **D3. The A14 rule: corroborated lag plus a sizing guard.** A quorum read (`#quorum`) is sized on every endpoint that passes the identity, identity-throttle, breaker and known-height filters; lag is **not** a reason to shrink it. It then measures lag against the **corroborated height**, the highest height that at least two of those endpoints have reached (their second-highest known height), never against one endpoint's claim, and leaves out an endpoint more than `maxLagBlocks` behind it. When fewer endpoints remain than the read needs, it decides nothing: a retryable `PROVIDER_UNAVAILABLE`, before any endpoint is asked. So one over-reporting endpoint can neither exclude honest endpoints nor be asked alone, and three endpoints with one liar still reach a quorum of two. Single (non-quorum) monitor reads and `status()` keep measuring lag against the best height (spec §11: "an endpoint beyond `maxLagBlocks` is excluded from monitor and scanner reads"). An endpoint with an **unknown** height (its probe failed) still does not count, as an open breaker does not: counting it would stall every proof for as long as one of two endpoints is down, since nothing sends it proof traffic. Costs: (a) with two endpoints, a genuinely lagging one is no longer dropped from proofs, which then wait until it has reached the proven fact (the facts are monotone predicates, lesson 17), instead of being served by one endpoint; (b) the handoff's N5 first half (a liar among the first two proof endpoints stalls verdicts) and second half (one absurd height makes every monitor view stale through `highestHeight()`) stay Plan 7 residuals.
- **D4. The A15 guard: in `appendSigned`, under a ref lease, against every other Operation.** `appendSigned` is the only place an Attempt is ever appended (original, replacement, cancel, rebuild). Once `assemble` has produced the ref, it takes a short lease `ref:<namespace>:<ref id>` through the existing `SequenceCoordinator`, asks the existing `store.findByRef(namespace, ref.id)`, and appends only when no **other** Operation holds that ref; the lease is released after the append. It refuses for a terminal holder too, not only a live one (A15 says "live"): a `final` or included-`failed` holder means those exact bytes are already on chain, so a second Operation would inherit their outcome, a phantom success for a payment that never moved. The refusal is `ChainError('NONCE_CONFLICT', 'the signed transaction is identical to another operation's transaction')`: the code that already means "this Operation's slot is taken" (`engine-rules.ts` uses it for input conflicts). An original Attempt's Operation then fails before any signed bytes are recorded (`failAfterPrepare`: nothing was persisted or sent, the nonce is released, the stored error is the refusal); a replacement, cancel or rebuild is dropped and the Operation keeps its active Attempt. There is no automatic rebuild: Plans 4 and 5 already vary every build (D5 there), so the guard fires only for a cross-process one-in-a-million collision or a deterministic third-party driver, and a new idempotency key resubmits. No store contract change. Cost: one lease round trip per appended Attempt.
- **D5. What the A15 guard guarantees.** With one `LockManager` shared by every process that writes the namespace (the setup nonce safety already requires), and an append that finishes within `lifecycle.leaseMs`, no two Operations of a namespace ever record the same Attempt ref id. It does not cover two namespaces (tenants are isolated by design), processes with separate lock managers, or an append that outlives its lease; and it compares ref ids, not transaction bytes (a malleated UTXO copy has its own txid and spends the same reserved inputs, which the `inputs` reservation already excludes).
- **D6. "The same plugin" (A18).** A plugin whose name is already registered is accepted again, as a no-op, only when it is the same object or structurally identical: equal data (chains, networks, presets, assets, schemes, manifest keys, capabilities and peer dependencies), with functions equal when they are the same function or have the same source text, and other class instances only by identity. `evmPlugin()` builds fresh manifests and closures on each call, so identity alone would make `new CryptoAio({ plugins: [evmPlugin()] })` throw (Review Focus 4). Anything else is `CONFIG_INVALID`, `plugin '<name>' is already registered with a different definition`. `Catalogs.plugins` becomes a `Map<string, Plugin>` (internal). Cost: two closures with the same source text but different captured values compare equal, so the second is still ignored; the guide says to give each plugin its own name.
- **D7. The A20 check is scoped to UTXO-model chains.** SLIP-0132 version bytes encode a Bitcoin network class (`xpub`/`ypub`/`zpub`/`Ypub`/`Zpub` mainnet; `tpub`/`upub`/`vpub`/`Upub`/`Vpub` test); account-model wallets do not (EVM and Tron wallets export `xpub` on every network, and the fake chain's `testnet: true` network already derives from an `xpub` in `test/core/container/handle.test.ts`). So `deriveXpubChild` gains an optional fourth parameter `network?: { readonly testnet: boolean }`, checked only for a known SLIP-0132 public version; `Blockchain.deriveAddress` passes it only when `chain.model === 'utxo'`. An unregistered version (an `xpubVersions` of another coin) has no known class and is not checked. The ruling's literal wording ("differs from `network.testnet`") would refuse every EVM testnet `xpub`; this is the recorded deviation. Cost: a UTXO family whose test networks use mainnet-class versions would need to call without `network`.
- **D8. The xpub reaches drivers as `WalletOptions.hd` (A22).** `walletOptionsOf(config)` adds `hd: { xpub, xpubPath?, xpubVersions? }`, a frozen plain copy, only when the wallet has an `xpub`. `hd` is reserved for the core: a wallet's own `options.hd` is dropped, with or without an `xpub`, because a driver trusts `hd` to validate change addresses. The member names are exactly the ones Plan 3 Task 8 Step 4b reads. The type `WalletHdOptions` is exported. Cost: none; an xpub is public data (privacy-sensitive, like an address list, and never emitted in events).
- **D9. The variant premise (A8, Plan 4 F11).** EVM, UTXO and Solana addresses carry no variant; Tron's `normalizeTronAddress` returns `variant: { hex }`, a pure function of `canonical`, so after A8 a Tron intent's hash includes it and base58 and hex inputs still hash the same. The frozen-hash test pins "an output without a variant hashes exactly as before", for four chains' address shapes, and Plan 4's e2e pins the Tron case. Cost: none.
- **D10. Failure reasons, with M8 (A9).** Plan 6 Task 1 as written: the monitor writes `reason` on every observed or proven inclusion patch, the driver's text for a failure and `undefined` otherwise, so a refusal's or an older failure's reason never survives a success.
- **D11. `submitSignatures` with a signed payload (A6).** Plan 3 Task 1 as written: the optional port `TxBuilder.signaturesFrom?`, `OperationEngine.requireOwned`, and the handle overload with a run-time `RawTx` shape check, ownership checked before the driver sees the payload.
- **D12. `CHANGELOG.md` is Plan 7's.** This plan lists its public additions and behaviour changes in the "Changelog block for Plan 7" section below and does not edit `CHANGELOG.md` or `README.md`. User-facing guide statements that this plan makes false or incomplete are fixed in the task that changes the behaviour (A18: the "ignored silently" sentence in `networks.md`; A6 and A15: `transactions.md`; A20: `concepts.md`), and Task 10 adds one list of driver notes for the driver-facing APIs (A6, A8, A9, A12, A22) to `networks.md`.
- **D13. The JSON-RPC error data under `exactIntegers` (A12, found while validating).** With the flag, a definitive JSON-RPC error whose `data` carries a big integer made `#unwrapRpc`'s `JSON.stringify` throw a `TypeError`, which `#classify` turned into a retryable, possibly-sent `PROVIDER_UNAVAILABLE`: a definitive answer (a simulation failure, a broadcast refusal) would have been retried and marked ambiguous. Task 1 writes a revived `bigint` in `details.rpcData` as a decimal string. Cost: `rpcData` quotes those digits, as diagnostic text only.
- **D14. A first-use identity probe goes before the request's token (A17).** With probes taking tokens but `#attempt` taking the request's token first, a first request on a fresh endpoint would still send the identity probe and the request back to back (the request's token was spent a second earlier). `#identityFirst` runs a pending identity check under its own deadline before the request's token wait; the check's failure is left to `#ensureIdentity` inside `#attempt`, so every error, breaker and throttle rule stays as it was. Cost: on first use, the identity probe has its own `timeoutMs` budget instead of sharing the request's.

### Task 1: Exact JSON integers for every JSON-bodied transport call (A12)

Rulings A11, A12 (amended). Source texts: Plan 5 Task 0 (`rpc`, `rpcRaw`, `http`) and Plan 4 Task 0 (`http`, `parseJson`), merged into one implementation and one test file (D1). Solana returns lamports and Tron returns sun as JSON **numbers**; above 2^53 − 1 `JSON.parse` rounds them, which breaks "bigint base units, never rounded". One gap both source texts missed is closed here: with the flag, a JSON-RPC error whose `data` carries a big integer made `#unwrapRpc`'s `JSON.stringify` throw, which turned a definitive `RPC_ERROR` into a retryable, possibly-sent `PROVIDER_UNAVAILABLE`.

**Files:**
- Modify: `src/core/util/json.ts` (add `parseJson`)
- Modify: `src/core/transport/types.ts` (`CallOptions.exactIntegers`)
- Modify: `src/core/transport/http-transport.ts` (thread the flag from `rpc`, `rpcRaw` and `http` to the JSON parse; `stringifyData` for error data)
- Test: `test/core/transport/exact-integers.test.ts`

**Interfaces:**
- Consumes: `HttpTransport` (`#rpcOnce`, `#httpOnce`, `#exchange`, `#unwrapRpc`), `FakeFetch`, `drive`, the transport test `setup` helper (`test/core/transport/support.ts`); Node ≥ 22 `JSON.parse` source-text access (`context.source` in a reviver).
- Produces:
  - `parseJson(text: string, exactIntegers?: boolean): unknown` in `src/core/util/json.ts`. With the flag, every integer literal outside `Number.MIN_SAFE_INTEGER..MAX_SAFE_INTEGER` becomes a `bigint` read from its source text; safe integers, fractions and exponents are unchanged.
  - `CallOptions.exactIntegers?: boolean` (default `false`). `Transport.rpc`, `rpcRaw` and `http` parse a JSON answer with it; a `quorumKey` sees the revived values; a JSON-RPC error's `details.rpcData` writes a revived `bigint` as a decimal string. Health probes (`EndpointCall`, `#direct`) keep plain parsing. Consumers: every Solana call (Plan 5 Task 2), every Tron call (Plan 4 Task 4).

**Review points:**
- Opt-in: without the flag every answer parses exactly as before (the "lossy without the flag" assertions); no existing reader sees a new shape.
- Only integer literals outside the safe range become bigints; `1.5`, `1e21`, `1e30` and safe integers keep their type.
- The flag reaches all three request paths and never the probes; the `http` assertion uses its own endpoint, so it pins parsing, not failover.
- A quorum over revived values compares exact integers (`canonicalJson` encodes bigints), so two answers that round to the same number disagree (Review Focus 1).
- A definitive JSON-RPC error stays a definitive `RPC_ERROR` when its `data` holds a big integer: `stringifyData` writes a `bigint` as a decimal string instead of throwing.

**Interfaces:**
- Consumes: `OperationEngine.require(operationId)`, `OperationEngine.assertOwnedBy(target, op)` (protected), `OperationEngine.submitSignatures(target, operationId, bundles)`, `RawTx`, `SignatureBundle`.
- Produces:
  - `TxBuilder.signaturesFrom?(unsigned: UnsignedTx, signed: RawTx): readonly SignatureBundle[]` (optional port, no I/O).
  - `OperationEngine.requireOwned(target, operationId): Promise<OperationRecord>`: `require` plus the engine's own chain, network and wallet check (`assertOwnedBy`).

**Review points:**
- The handle never trusts the signed payload: the only thing that reaches the engine is `SignatureBundle[]`, verified by the orchestrator exactly like bundles a user passes.

### Task 7: The AttemptRef uniqueness guard (A15)

Ruling A15 (found by Plans 4 and 5). Tron and Solana have no nonce: two different Operations with identical intents, built on the same reference block or blockhash, sign into byte-identical transactions. The second broadcast answers "already known", both Operations track one on-chain transfer and both end `final`/`executed`: one payment is silently lost. The fake `expiry` chain reproduces it exactly (the first test is red today for that reason). The guard (D4, D5) lives in `appendSigned`, the only place any Attempt is appended, and uses only existing store and lock APIs, so no store contract changes (see "Store-contract impact").

**Files:**
- Modify: `src/core/lifecycle/engine.ts` (the `AttemptRef` type import, `appendSigned`, new `withRefFree`, module-level `REF_HELD` and `refHeld`)
- Modify: `docs/guides/transactions.md` (the error table)
- Test: `test/core/lifecycle/attempt-ref.test.ts`

**Interfaces:**
- Consumes: `OperationStore.findByRef(namespace, refOrTxHash)` and `appendAttempt` (`src/core/store/types.ts`), `SequenceCoordinator.withLease(key, fn)` (`src/core/ordering/sequence.ts`, over the configured `LockManager`), `OperationEngine.failAfterPrepare`; `createFakeEnv({ ordering: 'expiry' })`, `FakeEnv.restart()`, `internalsOf(bc).pooled()`.
- Produces: no new API. An Attempt whose ref id another Operation of the namespace already holds (live or terminal) is refused with `ChainError('NONCE_CONFLICT', "the signed transaction is identical to another operation's")`, `details: { heldBy: <that Operation's id> }`. For an original Attempt the Operation ends `failed` with that error before any signed bytes are recorded (nonce released, as for a veto); a replacement, cancel or rebuild is dropped and its Operation is unchanged. - A holder is refused whether it is live or terminal (D4): a `final` holder means the bytes are on chain, and the second Operation would inherit that outcome. The Operation itself (`holder.id === op.id`) is never a conflict.
- Nothing is persisted or broadcast when the guard fires (the second Operation has no Attempt), and the first Operation is untouched.
- The refusal is recognised by identity (`REF_HELD`), never by its code, and it is a plain `ChainError` (its `name` is `ChainError`: a subclass would leak its own class name through `new.target`).
- Documented guarantee (D5): one shared `LockManager` and an append that finishes within `lifecycle.leaseMs`; it compares ref ids within one namespace.

/**
 * A18 (D6): whether two plugins are the same: the same object, or the same data and code.
 * Functions match when they are the same function or have the same source text (a factory
 * such as `evmPlugin()` builds fresh closures on every call); any other class instance
 * matches only itself.
 */
export function samePlugin(a: Plugin, b: Plugin): boolean {
  return sameShape(a, b, 0);
}

function sameShape(a: unknown, b: unknown, depth: number): boolean {
  if (Object.is(a, b)) return true;
  if (depth > 64) return false;
  if (typeof a === 'function' && typeof b === 'function') return String(a) === String(b);
  if (typeof a !== 'object' || typeof b !== 'object' || a === null || b === null) {
    return false;
  }
  if (Array.isArray(a) || Array.isArray(b)) {
    return (
      Array.isArray(a) &&
      Array.isArray(b) &&
      a.length === b.length &&
      a.every((item, i) => sameShape(item, b[i], depth + 1))
    );
  }
  const proto = Object.getPrototypeOf(a) as unknown;
  if (
    (proto !== Object.prototype && proto !== null) ||
    Object.getPrototypeOf(b) !== proto
  ) {
    return false;
  }
  const left = a as Record<string, unknown>;
  const right = b as Record<string, unknown>;
  const keys = Object.keys(left);
  return (
    keys.length === Object.keys(right).length &&
    keys.every(
      (key) => Object.hasOwn(right, key) && sameShape(left[key], right[key], depth + 1),
    )
  );
}

## Chain-specific risks

The protocol pitfalls behind these core changes, the families they hit, and how this plan handles each.

| Risk | Families | Handling | Task |
| --- | --- | --- | --- |
| Amounts above 2^53 − 1 base units are JSON numbers and `JSON.parse` rounds them (lamports, sun, energy) | Solana, Tron | Opt-in `exactIntegers` on every JSON-bodied call; quorums compare exact values; error data stays definitive | 1 |
| A keyless 1 request/second endpoint answers the back-to-back identity and height probes with 429, loses its height and is excluded ("no healthy endpoint") | TON (toncenter), Tron (TronGrid), Solana public RPC, Esplora | Probes take tokens from the endpoint's bucket; a first-use identity probe goes before the request's token | 2 |
| One endpoint that over-reports its head makes honest endpoints "lagging" and becomes the whole proof quorum, then attests its own head | All (every `quorum: 'proof'` read) | Quorum sized without lag; lag measured against the corroborated height; too few endpoints decide nothing | 3 |
| A PSBT (or other payload) signed by a cold wallet needs a two-step flow | UTXO first; any family later | `submitSignatures(id, RawTx)` through the optional `signaturesFrom` port; only signature bytes are trusted | 4 |
| The TON bounce flag (`EQ…` vs `UQ…`) is lost before the driver, so funds to an uninitialized wallet bounce or are deployed by balance against the caller's choice | TON | The address variant reaches drivers and is part of the intent hash | 5 |
| A bounce or failed action phase is `failed` with no reason; a refusal's reason survives a later success | TON first; any family | The monitor records the driver's fixed reason on failures and clears it otherwise | 6 |
| Identical transfers without a nonce sign into identical bytes; the second is "already known" and both Operations end `final` (a lost payment) | Tron, Solana (and any nonce-less chain) | The engine refuses to record one Attempt ref on two Operations, under a ref lease | 7 |
| A custom plugin reusing a registered name is dropped silently, so its chains never register | All (custom chain plugins) | `CONFIG_INVALID` unless it is the same plugin | 8 |
| A mainnet `xpub`/`zpub` on a Bitcoin test network (or the reverse) derives the wrong network's addresses | UTXO | SLIP-0132 class check on UTXO-model chains; EVM and Tron testnet `xpub`s keep working | 9 |
| Change sent to the wallet's own xpub chain needs an opt-out, because drivers never see the xpub | UTXO (A19) | `WalletOptions.hd` carries the xpub to drivers | 10 |

## Unresolved assumptions

1. **Unknown heights still shrink a quorum (D3).** An endpoint whose height probe failed does not count toward a proof quorum, as an open breaker does not. So a liar is the only proof endpoint when every honest endpoint's probe fails at once (an outage), exactly as today when their breakers are open. Default chosen for availability; cost if wrong: during a full honest outage, one malicious provider could decide proofs (the pre-existing availability trade-off of `quorum: 'proof'`, "capped by availability").
2. **N5's other halves stay open (Plan 7).** A liar among the first endpoints a proof asks stalls verdicts (`PROVIDER_INCONSISTENT` on every read), and one absurd height raises `highestHeight()` so every monitor view is stale. Both are liveness only; Task 3 closes the safety half.
3. **The A15 guarantee needs one shared lock manager (D5).** Processes with separate `LockManager`s, or an append that outlives `lifecycle.leaseMs`, can still both record a ref. `findByRef` is namespace-wide, not chain-scoped, so a ref id shared by two different chains of one namespace would be refused as a conflict; that needs a hash collision across chains, which no supported chain produces. Cost if wrong: one refused transfer, resubmitted under a new key.
4. **Probes do not wait out `Retry-After` (D2).** A probe waits for a token of the configured rate only. A server stricter than its configured `rateLimit`, or two endpoints of one host that share the server's limit (toncenter's v2 `rpc` and v3 `indexer` endpoints at 1 request/second each), can still answer a probe 429. For Plan 6: the keyless `public` preset's `rpc` and `indexer` together may send 2 requests/second to one IP limit of 1; either halve each (`rps: 0.5`) or keep the integration test's pauses. Cost: a probe failure clears the height until the next refresh.
5. **"The same plugin" by source text (D6).** Two closures with the same source text and different captured values compare equal, so the second plugin is ignored as before. Cost: a narrowed form of the old silent drop, documented in the guide.
6. **Unregistered extended-key versions are not classified (D7).** An `xpubVersions` that SLIP-0132 does not register (another coin's) is never checked, and a UTXO family whose test network uses mainnet-class versions would have to call `deriveXpubChild` without `network`. Bitcoin's test networks (testnet, testnet4, signet, regtest) use `tpub`-class versions.
7. **Policy hooks do not see the output variant.** `IntentSummary` (what `beforeSign` sees) is unchanged, so a hook cannot veto by TON bounce flag. Not asked for by A8; a Plan 7 candidate.
8. **The signed-payload path is proven with a stand-in extractor only.** No built-in driver implements `signaturesFrom` until Plan 3; its PSBT codec and e2e suite are the real proof.
9. **Plan 2's final shape.** Validated at Plan 2 `a4a9399`. If a later Plan 2 commit changes `http-transport.ts`, `engine.ts`, `monitor.ts`, `plugin.ts`, `hd.ts`, `wallet.ts` or the guides' anchored sentences before it merges, re-anchor on the same functions and sentences and keep this plan's content.

None. No store interface, contract suite assertion or classification changes:

- A15 uses `OperationStore.findByRef(namespace, refOrTxHash)` and the `LockManager` through `SequenceCoordinator.withLease`, both existing and already covered by `src/testing/contracts/*`.
